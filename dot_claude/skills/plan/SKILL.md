# plan: 設計・計画フェーズ

依頼を read-only で調査・整理し、`<現在の作業スペース>/plan.md` に**設計（Design）と計画（Phase 分割を含む段取り）**を本体が起草し、workflow の検証・レビューに掛けて、ユーザの承認を取って終了するスキル。実装には進まない（実装は呼び出し元の責務）。

「設計」と「計画」の両方を扱う:

- **設計（Design）**: 何をどう作るかの構造判断（データモデル・インターフェース契約・責務境界・依存方向・拡張点）。構造判断が要らない軽量タスクでは Design 節を立てない。
- **計画（Phase 分割を含む段取り）**: どの順序で進めるかの段取り（Phase ごとの目的・スコープ・受入・可逆性・接続）。1 コミット/1 PR で完結する軽量タスクでは Phase 節を立てない。

**責務の分担**: 起草は本体（main）の直営。検証・レビュー・出典付き訂正・リトライ収束は **plan-pipeline workflow**（`~/.claude/workflows/plan-pipeline.js`）に委譲し、件数集計・状態判定・恒等式は script が**コードで決定論的に実行**する（LLM の自己申告に依存しない）。

起草を本体直営にした理由: 前段（searing）と plan は原則同一セッションで直列に走り、premise を作った本体は調査知識を全部持っている。旧構造（起草を workflow の agent に委譲）では、その知識を agent に渡すために premise の「申し送り」への直列化が必要で、直列化の瞬間に事実と仮説の区別が潰れた——失敗接地: 実走で、申し送りに書かれた解形の一文（調査結果ではなく解の提案）が起草の設計の枠になり、設計判断レコードは全部その枠内の比較になった。前提自体の分岐は立たず、それを拾えたのはユーザの目的逆算の問いだけだった。本体が起草すれば仮説は文脈の中で流動的なまま設計まで運ばれ、直列化そのものが消える。

## 厳守プロトコル

- **`plan.md` を書く以外の Write は行わない。** 出力先は `<現在の作業スペース>/plan.md` 固定。
- 本体が使うのは Read/Glob/Grep/Write/Workflow/AskUserQuestion と、step 6 の閉じレビュー 1 体に限った Agent のみ。Bash/Edit と、それ以外の Agent は使わない（閉じレビューは単発の検査器であり、fan-out でも件数集計でもないため例外とする）。
- **起草・改稿を Agent や workflow に委譲しない（本体直営）。** 逆に、検証・レビューは workflow を介さず本体から直接 Agent で fan-out しない（オーケストレーションと件数集計を決定論層に置いた設計が骨抜きになり、LLM の自己申告ベースの集計に巻き戻る）。
- **workflow 戻りの `findings` を本体で要約・取捨・マージしない。** script が確定した生の N 件をそのまま per-item 列挙する（生の N 件＝提示の N 件）。
- 承認が取れたらこのスキルは終了する。実装系の作業は起動しない。

## 実行モデル

- `Skill` tool は **main 会話で動く**。skill フロントマターに `disallowed-tools` を**置かない**——フロントマター制限は main 全体に効くので、plan が active な間 /develop など呼び出し元まで巻き添えでツールを失う（失敗接地: 2026-06-11、develop からの呼び出しで develop 全体に Bash/Edit 制限が及ぶ構造を確認）。
- skill の指示による Workflow 起動は multi-agent orchestration の opt-in 要件を満たす（Workflow tool の仕様）。
- workflow は background で走り、完了通知で戻り値を受け取る。ユーザ対話（AskUserQuestion）は workflow 内ではできないが、起草は本体直営なので、起草中に見つかったユーザ限定の分岐はその場で聞ける（質問プロトコルに従う）。

## 質問プロトコル（全 step 共通）

AskUserQuestion をこのスキルから出すときは、step を問わず次の 2 つを通す。

### 事実先行ゲート

質問文が前提として含む事実（配備・リリースの順序・migration の実行系・DB 設定・既存挙動）は、質問より先に出典付きで確定させる。Read/Glob/Grep で確認できるものは確認してから質問し、確認できない運用事実は前提として断定文に書かない（「未検証」と明示して質問するか、分岐ごと Risks の未検証前提に載せる）。

- 失敗接地: 実走で、「配備系が migration をアプリより先に自動で流す」という未検証（実際には誤りで人手実行だった）の前提のまま DDL の適用時期を質問し、その回答の上に列定義と Phase 構成を積んだ。後から実測した時点で計画が覆り、同じ論点を再質問することになった。

### 裁量既定（規約から導ける確定は聞かない）

命名・画面文言・データ定義の流儀など、既存コードの流儀・規約・実測から一意に導ける創作的確定は AskUserQuestion に載せず、plan の「既定採用」節に既定値と根拠（出典 path）で列挙する。質問に載せるのは、業務仕様の選択・trade-off が拮抗する選好・premise の Open questions 由来の未決など、ユーザにしか決められない分岐だけ。判定基準は「その答えを既存流儀・実測から一意に導けるか」——導けるなら既定にし、導けないなら質問する。

- 失敗接地: 実走で、判定メソッド名・画面語彙・データ定義の流儀を 1 問ずつ質問した。流儀の実測までしておきながら質問に倒しており、「実装方針について細かく聞かれすぎている」というフィードバックを受けた。

## 起草・編集の事実規律（全 step 共通）

plan に書く実コードや運用についての事実主張は、起草時・承認往復の編集時を問わず、Read/Glob/Grep で実体を確認したものだけを事実の形で書く。呼び出し関係・経路・網羅性の主張（「全経路が X を通る」「呼び出し元はこの N 箇所」「この層で走る」）は特に、列挙した各項目を実際に読んで確認するまで plan に書かない。互換性・対称性のある性質（直列化互換・新旧バージョンの共存・双方向の変換）は**両方向を確認してから**「互換」「安全」と書く。確認していない推測を書く場合は推測と明示するか、Risks の未検証前提に置く。

- 失敗接地: 実走で、承認往復中に本体が「保存系メソッドを呼んでいるから版が増える」という推測から更新経路 6 つを plan に書き、うち 3 つが誤りだった。バリデーションを足す層も同名別系統のメソッドを取り違えた。
- 失敗接地: 実走で、「新キーなら旧セッションに存在しないので安全」と書いたが、これは旧データを新コードが読む方向だけの検証で、新コードが書いたデータを旧コードが読む逆方向（ローリングデプロイ中に必ず起きる）が抜けていた。事後の検査でも同じ片方向の枠が継承され、二重に外した。

## フロー

### 1. タスクの理解と出力先決定

- 依頼を整理する。曖昧点のうち Read/Glob/Grep で確定する事実は聞かずに調べ、ユーザにしか決められない分岐だけを AskUserQuestion で **1 問ずつ・依存順に**確認する（束ね打ちしない。searing の原則と同じ。premise.md がある場合は下記のとおりそもそも再質問しない）。
- **premise.md（searing の成果物）の読み込み**: 呼び出し元（/develop 等）や依頼文からパス指定があればそれを読む（主経路）。指定が無ければ同ディレクトリの `premise.md` を検出して読む（同一セッション連続実行のフォールバック。無ければ従来通り 1〜2 問確認する＝疎結合維持。ただし直前に searing を実行した文脈で見つからないときは、黙って従来経路に落ちずパスをユーザに確認する）。読んだら、その Purpose / Acceptance / Non-goals / Assumptions / Decisions / Open questions を step 1 の確認結果として扱う。premise.md の Open questions に挙がっていない軸は再質問しない。**Purpose / Acceptance は premise.md が正本——plan 側で再定義しない。** やる側の具体スコープ（Scope: In）は premise には書かれない（plan の領分）。
- **同一セッションで searing を実行済みの場合、premise 作成時の調査知識（読んだファイル・確定した運用事実・判明した設計材料）はこの文脈が既に持っている。premise.md に無いからといって捨てられていない——起草の入力としてそのまま使う。** 別セッションで作られた premise を受けた場合は、premise.md（目的と受入の正本）だけを引き継ぎ、調査は step 2 で自分でやり直す。
- **呼び出し元から skill-review レポートのパス指定があれば読む**（既存 skill 改修時の pre-plan 評価結果。step 2 の起草で改善対象の参照入力にする）。
- **premise.md の frontmatter `status` が `final` のものだけを確定済みとして扱う。** `status: draft` は searing が確定前に終わった形跡なので、そのまま足場にせず、続行可否をユーザに確認する。
- タスクディレクトリ名は作業スペースの命名規則に従う（チケットがあればチケット ID 起点、無ければ内容が一目で分かる日本語名）。**呼び出し元からタスクディレクトリ指定があれば命名規則より優先する**（実行台帳・premise.md との同居前提を壊さない）。
- 出力パス `<現在の作業スペース>/plan.md` をユーザに提示する。

### 2. 起草（本体直営）

本体が plan.md 全文を起草する。Agent に委譲しない。

**調査**: premise 段の知識を土台に、起草に足りない事実を Read/Glob/Grep で埋める。コードを grep する前にリポジトリ内の設計資料（docs/・README・CLAUDE.md・ADR 等）を当たり、DB スキーマは migration / DDL を一次ソースとする。変更対象のデータ（テーブル・エンティティ・永続化された構造）があるなら、書き込み経路（どの入口が同じ書き込みに集約されるか）と履歴・版管理の性質（追記型か・現行版を指すポインタ表の有無）を必ず確認する（失敗接地: 実走で、版管理イディオムの境界——どの操作が版を増やすか——をスポット読みからの推測で誤った）。

**運用事実の出典化**: 計画の決定に効く運用事実（migration の実行系・配備順序・DB 設定・デプロイ単位など）は repo 内の出典（path:line / 実測）で確認する。確認できない事実の上に Approach / Design / Phase の決定を載せない——載せるなら Risks に「未検証前提」として、何が未検証で覆えたら plan のどこが変わるかを明示する（失敗接地: 実走で、配備順序の誤前提の上に DDL の段取りと Phase 構成が載り、実測で計画が覆った）。

**分岐の扱い**: ユーザにしか決められない設計分岐（業務仕様の選択・trade-off が拮抗する選好）は、発見した時点で質問プロトコルに従い 1 問ずつ確認してから起草に織り込む（起草が本体直営なので、起草中でも聞ける）。既存流儀・実測から一意に導ける創作的確定は「既定採用」節へ。それ以外の設計分岐は設計判断レコードに記録して自分で選ぶ（承認ゲートで見える形にする）。見えていない分岐を推測で列挙しない。

**plan.md の構成**（設計と計画の両面を含める。該当しない節は立てない）:

必須節:
- **読みどころ**: frontmatter 直後に 5〜10 行。何を決めたか・ユーザの判断が要る分岐・主要リスクを、**本文の再記述ではなく参照**（「格納方式はレコード 3」「配備窓のトレードオフは Risks 2」の形）で書く。要約層は本文とドリフトするのが宿命なので、結論の写しを書かず索引に徹する（決定の単一表明と同じ原則）。
- **Context**: 背景と目的。premise.md があれば Purpose / Acceptance を踏まえる（premise が正本——再定義しない・抜き書きで足りる）。
- **Approach**: 推奨案のみを本文にする。代替案は並記しない（競合する選択肢があった事実と選択理由は設計判断レコードに記録する——本文から分岐を消しても、分岐があったこと自体は消さない）。
- **Critical files**: 変更対象のファイル（パターンが繰り返されるなら 1 回説明＋代表パス数件）。
- **Reusable utilities**: 再利用する既存実装（パス付き）。実在は統合ブランチ（既定 origin/main）基準で確認する。統合ブランチに無いものは「先行マージ待ち」か「自前新設」かを Approach に明記する。
- **Verification**: 実行・テスト方法。既存の検証手段を優先し、構築コストが対象の変更より大きい検証装置の新設を提案しない（検証の比例性。失敗接地: 受入条件の検証のために対象より巨大な仕組みを作ろうとし、ユーザが手動で止めた事例）。**TDD 適用宣言**: 変更がテスト可能なロジックを含み Acceptance が自動テストで観測できるなら、節の冒頭に「TDD 適用」と宣言し、Acceptance から導いたテストリスト（1 テスト = 1 振る舞い）を書く——implement がこの宣言を読んで `tdd: true` を既定にする。該当しなければ「TDD 不適用」と理由を 1 行書く。
- **Risks**: 未解消の Open questions・未検証前提・確定した前提が覆るリスク。premise の Open questions は起草で解消を試み、解消できなかったものだけここに繰り越す（未決論点の二重所有を避ける）。

条件付き節（該当しないなら節を立てない。「該当なし」「単一 Phase」と書いて空節を残さない）:
- **Design**: 構造判断の場。立てる条件（どれか満たす）: 新規データ構造が要る / 複数モジュールを跨ぐ / 非自明な責務分割が必要 / 既存抽象を変更する / 競合する設計選択肢がある。Design 節には**設計判断レコード**を含める: 検討した設計分岐ごとに {分岐・選んだ選択肢・捨てた選択肢と捨てた理由・判断が依存する事実と出典（依存が無ければ「事実依存なし」）} を 1 行ずつ記録する。**レコードの最上段には「前提の構え」の分岐を立てる**——並んだ分岐が全て同じ前提（既存構造の温存・特定の格納方式など）を共有していないかを起草時に自問し、共有しているならその前提自体を分岐として記録する（失敗接地: 実走で、レコードの全分岐が「2 つのデータを別々に持つ」前提を共有し、1 本に束ねる案が検討対象に入っていなかった。拾ったのはユーザの目的逆算の問い）。
- **Phase 分割**: 段取りの場。各 Phase に {目的, 変更スコープ, 受入条件, 可逆性, 次 Phase との接続} を書く。立てる条件（どれか満たす）: 1 コミット/1 PR で完結しない / 段階的に可逆性を担保したい / 部分デプロイで観測してから次に進みたい / 移行ステップが本質的に複数段。
- **既定採用**: 創作的確定（命名・画面文言・データ定義の流儀・メッセージの言い回し等）がある場合に立てる。各項目を {項目, 既定値, 根拠（既存流儀の出典 path）} で列挙する。

**complexity**: 呼び出し元から hint（light / heavy）が渡されていれば従う（light は Design / Phase を立てない、heavy は両方立てる）。無ければ上記の立てる条件で自分で判定する。軽量タスクに重い節を立てない——Design / Phase が膨張するとレビューもそれに引きずられる。

**決定の単一表明**: 一つの決定（データ定義・置き場・リリース単位・例外の扱い等）は設計判断レコードの 1 行を正本とし、他節では結論を再記述せず参照で済ませる（本文に書くのはその節の遂行に必要な帰結だけ）。同じ決定を複数節に再記述すると、後の訂正が片方だけ直して内部矛盾が生まれる（失敗接地: 実走で、複数節に再記述された決定 4 件が改稿のたびにずれ、全部が要判断ゲートに落ちた）。

**plan コードの深さの天井**: plan に書くコードは設計判断を運ぶ範囲（シグネチャ・データ構造・schema・不変条件・契約・非自明なアルゴリズムの骨子）に限り、関数本体の全文・ログ文言・エラー処理の書き下しは implement の領分。判定は「そのコードを消すと設計判断が失われるか」（plan のコードは未実行のまま正本の権威を帯び、implement の plan 突合がバグを「plan 通り」として通す経路になるため）。

**文書アーキテクチャ（読む層と調べる層の分離）**: plan は人間の承認者・implement・検証 agent の 3 者が読む。証拠の要求（出典・逐語・レコード）は本文への inline 堆積ではなく配置で満たす。(1) 出典（path:line / sha）を文中括弧で書かず、表の出典列・節末の出典リストに寄せる——機械照合（verify・逐語包含）は文書内のどこにあっても解決できるため、inline である必要は無い。(2) 1 パラグラフ 1 主張で、各節は結論の文から始める。Approach 本文は 10 行程度を目安にし、超える根拠は Design・参照側の節へ。必読（決定・分岐・リスク）と参照資料（根拠・棄却案・検証リスト）の密度を均一にしない。

- 失敗接地: 実走の plan が、全文均一の証拠密度と文中出典の堆積で法律文書化し、承認者が決定と分岐を拾うのに全文の再読を要した。規範はほぼ全部「書け」で「どこに置け」が無かったのが原因。

起草を終えたら `status: draft` の frontmatter で plan.md を Write し、その全文を step 3 に渡す。

### 3. plan-pipeline workflow の起動（検証・レビュー）

`Workflow` tool を以下で起動する:

- `scriptPath`: `~/.claude/workflows/plan-pipeline.js`
- `args`（JSON オブジェクトとして渡す。文字列化しない）:
  - `plan_md`: step 2 で起草した plan.md の全文（workflow script は filesystem を読めないため、パスでなく本文を渡す）
  - `repo_path`: 対象リポジトリのパス
  - `request`: 元の依頼文（step 1 の確認結果を織り込む）
  - `premise_path`: premise.md のパス（あれば）

パイプラインの構成（script 側に encode 済み・本体から重複指示しない）: 検証 (Explore)＋レビュー並列（該当節がある観点のみ評価）→ 出典付き訂正の適用 → severity:high が残る間のリトライ収束ループ（質的減少で停止・ハードリミット 2 回）→ 修正起点の二次整合チェック（1 回上限）。

### 4. 戻り解釈

workflow は以下を返す（件数・状態は script がコードで計算済み。schema は script 冒頭の定義を参照）:

```json
{
  "plan_md": "<plan.md 全文。出典付き訂正適用後の最終形>",
  "corrections_applied": [{"claim": "...", "reality": "...", "how_verified": "...", "severity": "...", "source": "path:line / sha", "corrected_text": "..."}],
  "unverified_marks": [{"claim": "...", "reality": "...", "how_verified": "...", "severity": "..."}],
  "findings": [{"id": 1, "round": 1, "summary": "...", "status": "problem", "severity": "high", "subtype": "none", "quote_text": "", "quote_verified": false, "resolved": false, "resolved_round": null, "state": "要判断"}],
  "totals": {"count": 0, "resolved": 0, "needs_decision": 0, "no_action": 0, "deferred": 0},
  "retry_log": {"rounds_executed": 1, "retries": 0, "stopped_by": "no-problem-high|quality-decrease-broken|hard-limit-2|nested-recheck-done|review-failed"},
  "flags": {"verify_failed": false, "review_failed": false}
}
```

本体の処理:

1. **sanity check（一瞥確認）**: `totals` の 4 値の合計が `findings.length` に一致すること。script 計算なので破れない設計だが、script 改変事故の検知としてだけ見る（不一致なら script のバグなのでユーザに報告して停止）。
2. **`flags` の確認**: `review_failed=true` ならレビュー未実施として per-item ゲートで明示する（「レビュー済み」を装わない）。`verify_failed=true` も同様に検証未実施を明示する。
3. `findings[].state` は script が確定した 4 状態（対応済み・要判断・対応不要・保留-設計上意図）。ラベルの張り替えによる再分類をしない（step 5 の前処理は plan への操作を伴う解消であって、張り替えではない）。

### 5. 訂正適用後の Write と per-item 判断ゲート

- **Write**: 戻りの `plan_md`（訂正適用後）で plan.md を上書きする。

#### 非設計指摘はゲートに出す前に処理する

`findings` のうち次の 3 類は、採否ゲートに出す前に本体が処理し、**処理済みの状態で全件列挙する**（件数保存。処理とは plan への操作——裏取り・修復・適用——を伴う解消であり、操作なしに state のラベルだけ書き換えることは従来どおり禁止）:

1. **出典付きの事実誤認**: レビューが実読の出典付きで示した plan の事実誤り、または本体が Read で裏取りして誤りと確定できる主張。plan を修復し、対応済みとして出典を併記する。出典が出せない・裏取りで確定しないものは要判断のまま。
2. **記述矛盾**: plan 自身の記述どうしの矛盾（同一対象への相互排他な言明の両在）で、勝ち側が (a) 統合ブランチ上の出典、または (b) plan 内の正本記述（設計判断レコードの行・premise の決定）との整合で一意に決まるもの。修復し、どちらを正としたかと根拠を併記する。どちらでも決まらない矛盾は要判断のまま。
3. **補完追記**: 既存の決定と矛盾せず、何も選ばず、plan の網羅性を上げるだけの追記（検証手順に 1 項・Risks に 1 項など）。適用した上で「適用済み一覧」として提示し、異議のある項目だけ外す（既定採用と同じ提示方式）。適用が検証工数を増やす場合はその影響を一覧に明記する。

残るのは**設計分岐**（何かを選ぶ・trade-off が拮抗する）だけで、これだけを採否として問う。

- 失敗接地: 実走で要判断 5 件のうち設計判断は 2 件だけだった。1 件は検証手順の 1 項追加、1 件は Risks の 1 項追加、1 件は出典付きの事実誤認で、採否を聞かれても採用以外の答えがほぼ無い。別の実走では本体が要判断 4 件全部を裏取りで解消しユーザ判断ゼロで通っており、この節はその振る舞いの固定。
- 失敗接地: 修復対象を記述矛盾だけに限っていた版では、自分が書いた記述の食い違いを採否として問い、「自身で記述した文言の不一致を設計判断とするのはおかしい」と指摘された。

#### 提示

- plan.md のパスを示し、検証/レビューサマリと**レビュー指摘の per-item 判断ゲート**を添えて承認可否を取る。**per-item 列挙は本文で行い、AskUserQuestion は採否入力（4 件以下）または反映後の最終承認に使う（提示と承認を同一 AskUserQuestion に押し込まない）**。
- **検証のサマリ**: 「検証で N 件修正（`corrections_applied`）・要確認 J 件（`unverified_marks`）」。適用された訂正は per-item に `source` と `corrected_text` を併記し、ユーザが目視で正確性を確認できるようにする（出典が本当にその訂正を支持するかは機械検証できないため、ユーザ目視を最後の砦にする）。
- **レビュー指摘の per-item 提示**: `findings` の生の全件を、1 件ずつ番号付きで {論点／深刻度／状態／反映するなら plan のどこを何に変えるか} で列挙する。4 状態の件数（`totals`）を列挙の前に明示し、合計が `findings.length` に一致することを示す。前処理で解消した指摘は解消済みとして根拠付きで列挙する。「保留-設計上意図」は採否でなく「v1 観測項目として plan に明示済みか」の確認として提示する。4 状態いずれも列挙の手前で消さない。
- **採否入力の手段**: 4 件以下なら AskUserQuestion の multiSelect でもよい。**5 件以上は本文に全件列挙し、番号指定で per-item に採否を答えさせる**。全指摘の列挙は常に本文で行う＝選択肢からの除外で指摘を落とさない。
- **既定採用の提示**: plan に「既定採用」節があれば、承認時に一覧として提示し、異議のある項目だけ上書きを受ける（項目ごとの AskUserQuestion に分解しない）。

### 6. 承認後の反映（経路選択）・閉じレビュー・引き継ぎ

採否が確定したら、反映の前に**経路を採否の深さで選ぶ**（当て込み一律にしない）:

1. **premise 矛盾 → searing 差し戻し**: 採否が premise の Purpose / Acceptance と矛盾する方向なら、plan 内で反映しない。plan.md は書き換えず、どの採否が premise のどこと矛盾するかを示して searing の再実行（premise の更新）をユーザに提案し、スキルを終了する。Purpose / Acceptance は premise が正本で plan は再定義しない契約——当て込みでも再検証でも吸収できない。
2. **設計判断レコードの選択差し替え → 再起草と再チェック**: 採用指摘の反映が、設計判断レコードに記録された選択を別の選択肢へ差し替えることを含むなら、当て込みにしない。本体が該当決定とその波及（Approach・Phase・Verification）を書き直し、書き直した全文で step 3 の workflow を再実行して検証・レビューを通し直す（差し替えは連鎖するため、検証を通らない当て込み経路で plan に入れない）。再実行は 1 回を上限とし、2 回目が要る状況は前提が揺れているシグナルとして経路 1 を疑う。
3. **それ未満 → 本体の当て込み**: 文言修正・個別 Phase の受入追記など、レコード上の選択が変わらない採用指摘は本体が plan の該当箇所に当てて反映する（**承認後 Write = 全文 Write 固定**）。起草・編集の事実規律に従う。採用指摘ゼロならこの Write はスキップ。

- 「保留-設計上意図」の項目は、採否でなく**「v1 観測項目として plan に明示する」ことが対応**——plan に observe-driven 宣言が既にあるか確認し、無ければ承認後 Write で該当節へ追記して終わる。

#### 閉じレビュー（最終確定の前に 1 回）

承認後の反映を終えた plan の最終形に対し、次のいずれかに該当する場合は最終確定の前に閉じレビューを 1 回実施する。(a) Design 節が立つ、(b) step 3 の検証を通っていない事実主張・設計記述を本体が承認往復で plan に書き足した（step 5 の前処理での修復・追記を含む）、(c) ユーザが明示的に求めた。いずれにも該当しない軽量 plan ではスキップしてよい。

- **形**: read-only を指示した Agent 1 体。入力は plan.md・premise.md・統合ブランチの実コード。fan-out しない・件数集計を任せない（厳守プロトコルの例外はこの 1 体だけ）。
- **重点順**: (1) pipeline 完了後に本体編集で入った記述の事実照合——呼び出し経路・層の特定・網羅性・互換性の主張は列挙された各項目を実読で確認させ、互換性は両方向を見させる、(2) シナリオ歩行（下記）、(3) 内部整合——相互排他な言明・設計判断レコードと本文の食い違い、(4) premise との整合。指摘には severity と、事実照合・内部整合・premise 整合は統合ブランチ上の出典（path:line）を必須とする。
- **シナリオ歩行**: plan の設計を、該当する定番シナリオへ一歩ずつ歩かせて帰結を導出させる——配備窓での新旧バージョン混在（互換は両方向）・同一データへの並行アクセスと多重実行・対象データが空/重複/旧版/巨大・部分失敗と後戻り（rollback・retry・再実行）・権限とテナントの境界（別ユーザ・別組織のデータに届く経路）。plan の変更に該当しないシナリオはスキップし、指摘ゼロは正当な出力（観点インフレ禁止と同じ規律）。**verify も review も「plan が主張したこと」しか照合せず、決定と運用事実を合成した帰結は誰も導出していない**——この歩行がその段。錨付けは plan の文ではなく「シナリオ＋依拠した実コードの事実（path:line）」で行う（帰結の指摘は欠落に紐づくため、文への錨は原理的に取れない）。
- **戻りの処理**: 指摘は step 5 と同じ規律で扱う（全件列挙・非設計指摘の前処理・設計分岐はユーザの採否）。**各指摘にどのレンズ由来か（事実照合／シナリオ歩行／内部整合／premise 整合）を明示させる**——レンズ別の内訳が無いと、閉じレビューの件数を起草品質の計器として読めなくなる。反映後に閉じレビューを再帰させない（1 回限り。再帰させると収束保証が無い）。
- 失敗接地: 実走で、承認往復中に本体が注入した事実誤認 2 件（更新経路の列挙・バリデーション層）を pipeline は検知できず、手動で差し込んだ単一文脈の設計レビューが指摘 5 件として拾った。標準化後の実走では、本体追記分の誤り 2 件を含む事実誤認 6 件を実装前に落とした。
- シナリオ歩行の失敗接地: 実走で、直列化互換の追加・ローリングデプロイでの新旧混在・デシリアライズ失敗時にセッション全体を捨てる既存実装、という 3 つの事実が個別には全部判明していたのに、誰も合成せず「配備中の強制ログアウト」という帰結が実装後のレビューまで残った。配備窓のシナリオを一歩ずつ歩けば plan 段で導出できた。

#### ナレッジ化候補の提示（終了時）

終了前に、`corrections_applied`・覆った運用事実・閉じレビューの事実訂正から、「書き残されていなかったから誤認された」知識（設計イディオム・命名の罠・運用事実）を選び、1 行ずつナレッジ化候補として提示する。**提示のみで Write はしない**（plan.md 以外の Write 禁止は維持）。置き場の判断が要るものは /knowledge-placement の利用を促す。候補ゼロならその旨を 1 行で言って終わる。**呼び出し元（/develop 等）から呼ばれた場合も省略しない**（orchestrator のフェーズ遷移に吸収させない——実走で、通しサイクル経由のとき plan フェーズ終了時のこの提示が発火しなかった）。

#### 引き継ぎ

- 反映が済んだらスキル終了。呼び出し元（main セッションまたは /develop）に plan.md のパスを返す。

## workflow との interface

正本は `~/.claude/workflows/plan-pipeline.js`（chezmoi source: `dot_claude/workflows/plan-pipeline.js`）。script 側を変更するときは本体節 step 3（args）/ step 4（戻り schema）との整合を確認する。

script に encode 済みの判断系規約（本体・script のどちらを変えるときも保持する。**モデルの能力ではなく判断方針の取り決めなので、モデル世代が変わっても削らない**）:

- **レビュー観点の節依存**: 評価観点は plan の節構成に応じて該当するもののみ評価。Design 節が無い軽量 plan で責務境界を指摘しない・Phase 節が無い plan で順序の可逆性を指摘しない。内部整合・検証十分性・暗黙の設計判断・前提の出典は常時評価。premise.md がある場合のみ目的整合を評価。
- **暗黙の設計判断レンズ**: 記録なしに片方へ倒された分岐を選択肢の形（a/b/c＋各 trade-off）で指摘して要判断に乗せる。レコードに並ぶ分岐が全て同じ前提を共有している場合、その前提自体が暗黙の選択でないかも見る（失敗接地: 2026-06-30 harvest 純関数化 plan。設計レベルの分岐 2 件が要判断に乗らず、記述レベルの指摘だけがゲートに届いた）。
- **検証の照合対象**: verify は現状認識の主張に加え、設計判断レコードの選択理由・却下理由・既定採用の根拠に埋まった事実主張（ライブラリの挙動・呼び出し関係・既存流儀の実在）も照合する（失敗接地: 実走で、却下理由に埋まったフレームワーク挙動の誤りを verify が拾わず、レビューが偶然拾って救われた）。
- **前提の出典**: 出典の無い運用前提の上に決定が載っていれば指摘する。plan 自身が Risks で未検証前提と明示しているものは指摘しない。
- **観点インフレ禁止**: レビューに「観点 N 個」「観点ごとに 1 件以上」の網羅指示を入れない。指摘ゼロは正当な出力。`status=problem-none`（supportive 含む）も findings に含めて母数を保つ。
- **severity:high の基準**: 目的を達成しない設計 / 致命的な手戻り構造 / Verification が不可能になる / plan の前提を覆す事実誤認 / スコープ外の再計画が必要。
- **deferred-by-design の意味論**: observe-driven の故意の未決を「曖昧 → medium」と読み替えない。逐語 `quote_text` 必須・script が `plan_md` への包含で機械照合し、落ちたら「要判断」へ demote。
- **出典なき自動修正の禁止**: 訂正は統合ブランチ（既定 origin/main）上の出典（path:line / sha）を伴うものだけ適用。出典が無い不一致は（要確認）マークで保留。
- **統合ブランチ基準の実在確認**: 「実在」「再利用可」は統合ブランチ基準。並走 worktree の grep で断定しない。
- **改稿の範囲制約**: revise agent は指示された訂正・指摘の範囲だけ plan を書き換える。ただし指示対象が複数箇所に再記述されている場合は全箇所に同じ訂正を当てる（片方だけ直して矛盾を残さない）。medium/low はユーザ判断に委ねるため retry 改稿で触らない。
- **リトライの停止判定**: 質的減少（open high の厳密減少 AND open total の非増加）を script が不等式で判定。ハードリミット 2 回は暴走防止の保険。
- **改稿 agent への文体注入**: revise agent は `~/.claude/output-style.md` を Read して新たに書き足す地の文を従わせる（workflow agent は main の常時ロード規範を継承しない）。

起草側の規範（節構造・読みどころ・文書アーキテクチャ・設計判断レコード・決定の単一表明・既定採用・運用事実の出典化・資料先行・検証の比例性・TDD 宣言・コードの深さの天井）は step 2 に置く——起草が本体直営になり、これらは script ではなく本体の規範になった。同じく判断方針の取り決めなので削らない。

## 撃ち直した残差の記録（構造変更で前提条件が消えた防御）

旧設計の失敗接地由来の防御のうち、以下は**構造変更で前提条件が消えたため撤去した**。元の失敗が新構造で再発したら、該当の錨ごと復活させる:

- **件数保存則の二段アサート**（失敗接地: 2026-06-09 の要判断 0 事故）→ `totals` を agent に申告させず script が `findings.length` から計算する構造になり、母数絞り・状態畳みが構造的に不可能になった。本体 step 4 の sanity check は script 改変事故の検知用に残置。
- **JSON fenced block 規約・型コアース・schema 逸脱時の再実行**→ `agent(prompt, {schema})` の structured output が tool 層で validate するため不要。
- **nested_markers 機構一式**（失敗接地: [[subagent のネスト起動は親から見えない]]）→ agent の spawn が workflow script の決定論コードになり、観測ギャップ自体が消滅。
- **`auto_corrections_applied[].source` の強検出/弱検出 regex**（失敗接地: 2026-06-11 の越権 2 回観察）→ 検証とレビューが独立並列の別 agent になり、レビュー指摘が検証出力に混入する経路が構造消滅。
- **planner-agent と disallowedTools**→ 中間管理 LLM 自体を廃止（オーケストレーションは script）。
- **起草の workflow 委譲と「plan への申し送り」経路**（2026-08-01 撤去）→ 起草を premise と同一文脈の本体直営に変更し、premise から起草への直列化そのものを廃止。失敗接地: 実走で、申し送りに書かれた解形の一文が設計の枠になり、前提自体の分岐が立たなかった。元の失敗（本体起草の plan が検証・レビューで救えない水準に落ちる）が再発したら委譲と申し送りを復活させる。
- **起草 agent への文体注入・調査結果のレビュー受け渡し・complexity hint の script 意味論**（2026-08-01 撤去）→ 起草・調査が本体に移り、起草には常時ロードの output-style が直接効く。explore 段の廃止で受け渡す調査結果自体が消滅（レビューの文脈補完は premise 参照と暗黙の設計判断レンズの前提共有チェックで代替）。節立て判定は本体が step 2 で行う。

## やってはいけないこと

- plan.md 以外を Write する
- 承認後に自分で実装に進む（agent / workflow 起動含む）
- 出力先を `.claude/plans/` にする
- EnterPlanMode を呼ぶ（このスキルは plan モードを使わない設計）
- **skill フロントマターに `disallowed-tools` を置く**（`Skill` tool は main で動くため、呼び出し元まで巻き添えでツールを失う。失敗接地: 2026-06-11）
